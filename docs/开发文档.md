# 像素拼图 · Windows 版 —— 开发文档

> 面向接手维护的人。讲清**为什么这么做**，不只是"是什么"。
> 用户手册见 [README.md](README.md)。

---

## 1. 项目定位

把 N 张照片 1:1 无损拼成一张画布 → 送进像素蛋糕精修 → 按记录精确切回 N 张原图。

**核心矛盾**：像素蛋糕按"单张画布"扣费，而一张画布能装多张照片。
几何上受**单边像素上限**约束（不是总面积），所以这是个装箱问题。

**不能做的事**：拼完再拆不能用于液化／AI 天空／消除／裁剪——这些是几何变形或生成式重绘，
拆开后像素不可逆，且人脸/肤色按整画布统计会串味。详见 §3.3。

## 3. 核心概念

### 3.1 三级上限

| 常量 | 值 | 来源 | 用途 |
|---|---|---|---|
| `PIXCAKE_HARD_LIMIT` | **13000** | 反向实测：导入校验 `cmp eax, 0x32c8` | 超过弹窗警告，引导回落 12000 |
| `PIXCAKE_SAFE_LIMIT` | 12000 | 与官方素材链路一致 | 默认值 |
| `PIXCAKE_TEXTURE_LIMIT` | 16384 | `GL_MAX_TEXTURE_SIZE`（随显卡变） | **语义仅为「GPU 纹理上限」**，超了只静默降采样 |
| `v_maxside` | 用户可调 | UI | 实际使用 |

**为什么 13000 才是硬闸门**：13000 是「进项目」这一步的校验值，超了直接弹
「暂时只支持导入长宽在 100~13000 像素区间的图片」——**连静默降采样的机会都没有**，
整批白拼。16384 只是 GPU 纹理上限，超过它的图会被悄悄降分辨率，不是导入门槛。
早期把 16384 当上限是错的（`docs/README.md` 旧版同误，已改）。
默认取 12000：与官方素材链路同门，留 1000px 余量给保护带与多张图的零头。

### 3.1b 朝向优先（修人像的关键）

`orientation_of(w,h)` → `P`（竖，h>w）/ `L`（横）/ `S`（方）。`SourceImage.orientation`
按 `natural_w/natural_h` 判断，而这两个值来自 `probe_image()`（已 `exif_transpose`），
所以「真实朝向」就是「人脸朝上时的朝向」。

**默认零旋转**：竖屏照片竖着排、横屏照片横着排，`Placement.rotation` 恒为 0，
人脸端正、像素蛋糕的人脸识别不会失效。密度靠**横竖混排**拿，不靠旋转：

| A7M4（横 7008×4672 / 竖 4672×7008，gutter 12，上限 12000） | 单画布张数 |
|---|---|
| 全横 | 2（2 行 9392；3 行 14088 ✗，2 列 14064 ✗） |
| 全竖 | 2 |
| **1 竖列 + 1 横列（混排）** | **3**（4696 + 7032 = 11728 ≤ 12000，横列叠 2 张 = 9392） |

**「允许旋转 90°」是可选增益**：开了之后由**排版器**决定哪几张转（不是无脑全转），
纯粹用来把「全横批」这类 2 张的画布提到 3 张。代价是那几张人脸侧躺 —— 修人像请勿开。

### 3.2 保护带（gutter）

每张图**四边 + 四角**向外铺自身镜像，默认半宽 12px。

**为什么需要**：M0 实测证明液化的形变是**全局平滑位移场**，不会停在笔刷边缘，
会跨过接缝衰减（峰值 5px → 跨接缝后 <1px）。

**为什么填自身镜像而不是灰色/隔壁图**：
位移场拉扯边缘像素时，如果填的是灰色或邻居，被"换掉"的就是隔壁的内容；
填自身镜像 = 被拉扯时取到的还是自己的延伸像素。

**为什么四角也要**：混尺寸装箱会产生 L 形空隙，只铺四条边会在拐角留下灰底，
灰底被拉进画面就是污染。

**为什么排班时要按 `w+2g × h+2g` 占位**：保护带被压住 = 没有保护带。
`_valid_layout()` 强制检查这一点（`tiler_core.py: _valid`）。

### 3.3 操作白名单（写进 UI，不靠记性）

| 安全 | 危险 |
|---|---|
| 曝光、对比、高光阴影 | 液化、脸型、瘦身 |
| 白平衡、色温色调 | AI 天空 / 换背景 |
| 曲线、HSL、分离色调 | AI 消除 / 扩图 |
| 纯色彩类预设、滤镜 | 裁剪、排版印刷 |

**判据**：逐像素静态映射 → 拆回来各自带走，跨缝不污染；
几何变形 / 生成式 → 不可逆 + 语义错乱。

## 4. 算法

### 4.1 排版（`pack_canvases`）

```
输入: srcs[], max_side, gap, gutter, allow_rotate, time_budget_ms
0. 下界 lb = max( ceil(总面积 / 可用面积), ceil(N / 单画布容量上界) )
   达到 lb 立即收工（已是数学最优）；allow_rotate 默认 False
1. 多起点：5 套确定性排序（面积 / 长边 / 朝向优先竖图 / 朝向优先横图 / 短边）
2. 每套起点做贪心装箱（first-fit-decreasing）：
   依次尝试塞进已有画布组，塞不进才开新组；每次尝试调用 _try_pack()
   剪枝：① 块面积之和 > 画布面积 → 跳过（严格成立）
         ② 只试投最空的 16 个画布（_GREEDY_SCAN_CAP）
         ③ 画布张数已达单画布上界 → 跳过
3. 对每组再跑一次 _try_pack(effort=2)（画布数已定，求最小包围盒）
4. 画布合并：任意两张能并成一张就并（同样带①②③剪枝）
5. 搬空重填：把最空的画布拆开逐张塞进别的画布，全塞下就撤掉它（失败则回滚）
6. 取「画布数最少，其次总面积最小」的起点作为结果
```

### 4.2 row / col 版式（`pack_strip`）

row = 全部横排成一行；col = 全部竖排成一列。与 `pack_canvases` 的唯一差别是
**绝不重采样**：

```
输入: srcs[], max_side, axis, gap, gutter
1. 每张图取旋转后的原始像素尺寸（row 取 w×h，col 取 h×w）
2. 沿排列方向贪心装箱：这张图「右边界 + 保护带」超过 max_side 就开新画布
   每个画布仍是一行 / 一列（不是退回 grid）
3. 同一画布内交叉轴（row 是高、col 是宽）取最大值作为「带」，各图居中，
   多出来的部分留背景色
```

**为什么这样改**（原实现有两个 bug）：
- 原实现按 `min(高)` / `min(宽)` 等比缩放每张图 → manifest 记的 crop 尺寸 ≠ 原图尺寸，
  切回来是重采样过的像素，违反「1:1 无损」承诺，且没有任何告警。
- 原实现完全不校验单边上限 → 10 张 6000px 横排 = 60000px 画布照导不误。

**等价性**：同机型同朝向的照片交叉轴尺寸相同，此时「留白对齐」与「等比缩放」
结果完全一致——所以这次改动对最常见的用法**零视觉变化**，只有混排时才从
「悄悄缩图」变成「留白」。

**单张放不下**：单张图自身「主轴 + 2×保护带」超过 `max_side` 时直接抛
`ValueError`，提示调高单边上限或改用 grid。

**实测**：A7M4 5 张（3横2竖混排）row → 3 张画布，切回逐像素偏差 = 0。

### 4.3 `_try_pack` 的三层候选

```python
keys = [8 种排序键]        # 高/宽/面积/长边/周长/短边 + 朝向优先(竖)/朝向优先(横)
orders = keys + 24 次随机打乱
for order in orders:
    for algo in (_shelf, _maxrects, _bands):
        pos, rots = algo(...)
        if 合法: cand = _compact(pos)      # 紧包围盒重压
        取面积最小的
```

- **`_shelf`**：货架式，一行一行排。快，适合同尺寸。
- **`_maxrects`**：MaxRects + best-short-side-fit。适合混尺寸。
- **`_bands`**（V3 新增主力）：**朝向感知列带分解**——「竖屏竖着排、横屏横着排」
  的几何实现。把画布切成若干竖直列，列宽 = 列内最宽块，列内竖向堆叠。
  竖图窄、横图宽，混排时宽度恰好互补（A7M4：1 竖列 + 1 横列 = 11728 ≤ 12000
  → 同画布 3 张，且**一张都没转**），对均匀批次直接拿到数学最优。
  `allow_rotate=True` 时才允许个别块转 90° 塞进窄列。
- **`_compact`**：排完后按 `(y, x)` 顺序把每张图往上、往左挤到不能再挤。
  这一步是填充率从 ~75% 提到 ~89% 的关键。

**旋转由排版器决定**：`pack_canvases(allow_rotate=)` 是唯一入口，`_bands` 按需
决定哪几张转；`Placement.rotation` 落进 manifest，切分时 `rot==90` 转回。
GUI 不再预先改写 `SourceImage.rotation`（旧版一开开关就把**所有**横图转 90°，已修）。

**确定性**：随机种子固定（`random.Random(20240101)`），同一批照片每次结果一致。

**实测**（上限 12000 / gutter 12 / 默认不旋转）：

| 批次（A7M4） | 画布数 | 每画布张数 |
|---|---|---|
| 12 张全横 | 6 | 2（不旋转的几何上限） |
| 12 张全横 + 开旋转 | 4 | 3 |
| 6 横 + 6 竖 | 5 | 3,3,2,2,2 ＝ **数学最优** |
| 60 横 + 30 竖 | 30 | 3 ＝ 数学最优，4.9s |
| 120 横 + 60 竖 | 60 | 3 ＝ 数学最优，13.7s |

> 6 横 + 6 竖 之所以最优只能到 5 张画布（而不是 12/3 = 4）：A7M4 的 3 张画布
> 只可能是「1 竖 + 2 横」这一种组合（2 竖 + 1 横 宽度 16424 ✗，3 竖 14088 ✗），
> 4 张画布需 4 竖 + 8 横，而手里只有 6 竖 6 横 —— 不可行。

### 4.3b `verify_plan` 校验（`self_test` 调用）

不重叠（按 `w+2g × h+2g` 占位算）/ 不超单边 / 内容与保护带都在画布内 /
**未旋转时占位尺寸必须等于原图尺寸**（保证人脸是正的）/ 旋转时等于原图转置 /
`rotation` 只能是 0 或 90。

### 4.4 合成（`compose_canvas`）

```
canvas = Image.new("RGB", (w, h), 灰色)
for 每张图:
    读图 → EXIF 摆正 → 可选旋转 90° → 尺寸不符才 resize 到占位尺寸
    先贴 8 个镜像小条（四边四角）
    再贴真实内容（顺序不能反！）
写 .part → os.replace 原子替换
```

**resize 只是兜底**：grid / row / col 的占位尺寸都等于「旋转后的原图像素尺寸」，
所以正常路径这里是空操作——这正是切回来能 1:1 无损的前提。一旦这里真的触发了
resize，说明占位被改成了非原图尺寸，切回必然不是原像素。

**为什么必须先贴镜像**：tkinter/PIL 的 paste 是覆盖式，顺序反了镜像会盖住内容。

**为什么强制 RGB**：RGBA 会让 TIFF 体积多 25%，且下游切分按 3 通道读会错位。

### 4.5 切分（`split_canvas`）

```
1. 读 manifest（绝对矩形 + 源 sha256）
2. 尺寸校验：
   - 尺寸一致        → 精确 crop（1:1 无损）
   - 等比缩放        → 按比例映射 + 告警（有一次重采样）
   - 宽高比不一致    → 抛异常，拒绝
3. 逐张 crop → 可选转正 → 编码
4. 重名不覆盖（自动加 _1）
5. 单张失败不拖垮整批（记 error 继续）
```

**绝不猜着切**：manifest 配不上就拒绝，不按文件名前缀模糊匹配——
`batch2.tif` 匹到 `batch.manifest.json` 会切出全错的图。

## 5. 数据格式

### 5.1 manifest（`TILE_xxx_c01.manifest.json`）

```json
{
  "app": "pixcake-tiler-win",
  "version": 5,
  "created": "2026-10-19T13:20:00",
  "batch": "a1b2c3d4e5",
  "canvas": {
    "file": "TILE_a1b2c3d4e5_c01.tif",
    "width": 10072, "height": 9048,
    "gutter": 12, "gap": 0, "maxSide": 12000
  },
  "settings": {
    "rotateUsed": false,
    "pixcakeExportFormat": "TIFF",
    "camera": "Sony A7 IV (33MP)"
  },
  "items": [
    {
      "index": 0,
      "source": "D:/photos/DSC_1001.jpg",
      "name": "DSC_1001.jpg",
      "format": "jpeg",
      "natural": { "width": 6000, "height": 4000 },
      "rotation": 0,
      "crop": { "left": 12, "top": 12, "width": 6000, "height": 4000 },
      "sha256": "...",
      "shotTime": "2026:05:01 10:20:30",
      "model": "ILCE-7M4",
      "exifKind": "app1",
      "exifB64": "RXhpZgAATU0..."
    }
  ]
}
```

**关键约束**：
- `crop` 是画布内**绝对像素矩形**，切分时直接 `im.crop()`。
- `canvas.width/height` 必须与导出图尺寸一致，否则走比例映射。
- `version` 变化时 `split_canvas` 需要兼容旧版本。
- **v5 新增** `shotTime` / `model` / `exifKind` / `exifB64`（base64）。
  把 EXIF 内嵌进 manifest 是为了**源图归档、改名、移走后仍能写回拍摄信息**——
  原来只从 `source` 路径重读源图，源图一不在 EXIF 就没了。
  `split_canvas` 取用顺序：manifest 内嵌 `exifB64` → 回落到源文件路径 → 都没有则记 `exifNothingToCopy` 并告警。
- 读 v4 旧 manifest 时 `exifB64` 为空，自动走老逻辑，旧文件仍可使用。
- 体积代价：带 MakerNote 的 APP1 约 30–70KB，base64 后 ×1.33，一张 6 图画布约 400KB。

### 5.2 账本（`ledger.json`）

```json
{
  "batches": [
    { "batch": "a1b2", "time": "...", "images": 5, "canvases": 2,
      "savedShots": 3, "removed": false, "camera": "Sony A7 IV" }
  ]
}
```

`savedShots = images - canvases`。`removed: true` 表示这条是白做的测试，从统计里剔除。

## 6. 关键实现陷阱（踩过的坑）

### 6.1 `启动.bat` 必须是 ASCII + CRLF

UTF-8 + LF 会让 `title` 行吃到下一行，`cd /d "%~dp0"` 被吞，脚本在错误目录执行。
**铁律**：bat 文件里不写中文，换行用 `\r\n`。

### 6.2 三栏布局用 grid 不用 pack

`pack(side="left"/"right")` 按装入顺序切分空间。窗口一变窄，
后装的右列会被挤出屏幕（实测 1440px 宽时右列只在 1400 处开始）。

**正确做法**：
```python
body.grid_columnconfigure(0, weight=0, minsize=330)
body.grid_columnconfigure(1, weight=1)              # 中列吃剩余
body.grid_columnconfigure(2, weight=0, minsize=340)
```

### 6.3 高 DPI 必须在创建 Tk 之前声明

本机 2560×1440 物理屏 + 125% 缩放 → 逻辑坐标只有 2048×1152。
Tk 不声明 DPI 感知的话，系统会把整个窗口位图拉伸，字发虚，
而且 `winfo_screenwidth()` 返回的是缩放后的值。

```python
ctypes.windll.shcore.SetProcessDpiAwareness(2)   # 必须在 tk.Tk() 之前
root = tk.Tk()
```

### 6.4 窗口尺寸要按屏幕真实分辨率夹

```python
w = min(1440, max(1300, int(sw * 0.86)))   # 左330 + 中600 + 右340 + 边距
w = min(w, sw - 40)
```
硬编码 1440 在 125% 缩放下会超出屏幕。

### 6.5 线程 → UI 只能走 `root.after`

Tk 不是线程安全的。`Worker` 用 `queue.Queue` 收集进度，
主线程 `after(60)` 轮询取出再更新控件。

### 6.6 关闭时要停掉回调

`self.closing` 标志 + 所有 `root.after` 回调里先判空，
否则销毁时后台任务回来会报 `invalid command name`。

### 6.7 拖放需要 `WM_DROPFILES` + WndProc 子类化

tkinter 原生不支持文件拖入。用 ctypes 替换窗口过程：
```python
u.DragAcceptFiles(hwnd, True)
old = u.SetWindowLongPtrW(hwnd, -4, 0)
proc = WNDPROC(handler)          # 必须保持引用，否则被 GC
u.SetWindowLongPtrW(hwnd, -4, cast(proc, c_void_p))
```
**注意**：`self._proc` 必须存成实例属性，局部变量会被回收导致崩溃。

### 6.8 EXIF 搬运走双通道

**JPEG 源图**：不用 PIL 的 `exif=` 参数（会破坏 ISO/光圈/快门），
直接取 APP1 段原始字节插入，这样厂商私有 MakerNote 能原样保住。

**非 JPEG 源图（TIFF / PNG / WEBP）**：走 Pillow 原生通道 `getexif()` 提取。
最早这里只认 JPEG 魔数 `\xff\xd8`，源图是 TIFF 时直接返回 `None`，
**切回的图一点 EXIF 都没有且不报错**——这是已修复的真实缺口。

两条通道字节格式不同，用 `extract_exif_blob()` 的返回值区分：
`("app1")` 是完整 APP1 段（含 `\xff\xe1` + 长度），`("raw")` 是自带 `Exif\0\0` 头的裸块。
写回收口在 `apply_exif_to_output()` / `save_exif_kwargs()`，不再散落 `if outfmt == "jpeg"`。

搬运时做两件事：
- **摘缩略图**：把 IFD0 的 next-IFD 指针（`ifd0 + 2 + count*12`）清零，
  否则客户在资源管理器看到的是没修过的旧缩略图。
- **Orientation 归一为 1**：导入时方向已烤进像素，再搬回 `Orientation=6`
  会让看图软件转第二次 → **竖拍交付时躺倒**。

读 EXIF 时注意 `DateTimeOriginal(0x9003)` / `LensModel(0xA434)` 在
**ExifIFD 子目录**（`get_ifd(0x8769)`）里，直接 `getexif().get()` 取到的是 `None`。
用 `_exif_lookup()` 先查 IFD0 再查子目录。

**TIFF 输出的已知限制**：Pillow 的 TIFF 编码器**写不了 ExifIFD 子目录**——
传 `exif=` 会因 `EXIFIFDOffset` 直接报错，传嵌套 `tiffinfo` 也会失效（实测 12.2.0）。
所以 TIFF 输出只能经 `tiff_ifd0()` 写 IFD0（机型 / 拍摄时间 / 软件 / Orientation），
光圈 / 快门 / ISO / 镜头 会在切回报告的 `warnings` 里明确告知。
需要完整 EXIF 请选 JPEG 或 PNG 输出。

**导入时一次提取并缓存**（`attach_exif()`），把结果存进 `SourceImage.shot_time` /
`model` / `exif_b64`，并随 manifest 落盘，避免切分时依赖源图仍在原地。

### 6.9 `_mirror_strips` 顺序

先贴镜像、后贴内容。反过来镜像会盖住内容。

## 8. 扩展点

### 8.1 加相机预设

`tiler_core.CAMERA_PRESETS` 加一行：
```python
"Sony A7 V (33MP)": {"w": 7008, "h": 4672},
```
UI 的 Combobox 自动带上（读的是 `list(CAMERA_PRESETS.keys())`）。

同时建议在 `tiler_core.CAMERA_MODEL_HINTS` 加一条机型串映射，
这样 import 照片时能优先按 EXIF 的 `Model` 识别，而不是靠像素尺寸猜：
```python
("ILCE-7M5", "Sony A7 V (33MP)"),
```
映射目标必须是 `CAMERA_PRESETS` 里已存在的 key。
识别取「匹配位置最靠后」的一条，所以泛称（如 `EOS R`）不会抢走 `EOS R5`。

### 8.2 换排版算法

实现 `algo(sizes, max_side, gap, order, gutter) -> [(x,y)] | None`，
加进 `_try_pack` 的 `for algo in (...) `。返回坐标必须是**内容左上角**（不含 gutter）。

### 8.3 加切分输出格式

`split_canvas` 里 `outfmt` 分支 + `ext` 映射表。

### 8.4 把账本改成 SQLite

`ledger_add` / `ledger_summary` 两个函数是唯一入口，替换实现即可。

## 9. 性能

| 场景 | 实测 |
|---|---|
| 排版 5 张 | < 200ms |
| 合成 10072×9048 | ~8s（LZW） |
| 切分 5 张 | ~1.5s |
| 峰值内存 | 画布 + 一张源图 |

**已知瓶颈**：
- 合成是**串行**贴图（PIL 没有并行 paste）。要快只能多进程，但画布数通常 1-3，
  收益低于复杂度成本，暂不做。
- LZW 压缩单线程，这是 Pillow 的架构限制。
